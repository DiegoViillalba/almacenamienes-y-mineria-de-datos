6  Data Lakehouse

6.1 Introducción a la Arquitectura Lakehouse

Como se discutió en el capítulo anterior, tanto el Data Warehouse (consistente pero rígido y costoso) como el Data Lake (flexible pero propenso al desorden y sin soporte transaccional) presentan desafíos importantes para los equipos modernos de datos. Para unificar el rendimiento SQL y la gobernanza del DWH con el bajo costo y la escalabilidad del Data Lake, surge la arquitectura del Data Lakehouse.

Esta caracterización describe tendencias históricas, no reglas absolutas: existen Data Warehouses elásticos y Data Lakes bien gobernados. El problema aparece cuando una organización mantiene ambos como mundos separados. Los datos se copian del lago al almacén para producir reportes; después se vuelven a preparar para ciencia de datos. Cada copia agrega latencia, costo y la posibilidad de que dos equipos trabajen con versiones diferentes de la realidad.

El Lakehouse puede entenderse como una evolución natural del Data Lake. Mantiene el almacenamiento de objetos, su capacidad para recibir datos diversos y la separación entre almacenamiento y cómputo, pero incorpora una capa de tablas, metadatos y gobierno capaz de ofrecer transacciones, esquemas, control de acceso y consultas SQL confiables. No consiste en colocar un Data Warehouse junto a un Data Lake, sino en hacer que los datos del lago se comporten como tablas administradas sin perder su apertura y flexibilidad.

Datos de cualquier tipo, almacenamiento económico y acceso flexible para ingeniería y ciencia de datos.

🗂️

Evolución conceptual. El Lakehouse añade semántica y confiabilidad al almacenamiento flexible del Data Lake.

6.2 Lo mejor de dos tradiciones

El término Lakehouse expresa una convergencia. Del Data Lake conserva la escala, el costo del almacenamiento de objetos, la variedad de formatos y el acceso desde distintos motores. Del Data Warehouse recupera las garantías necesarias para que los datos puedan utilizarse como producto empresarial: calidad verificable, modelos entendibles, consultas concurrentes y gobierno centralizado.

🌊
Del Data Lake
Escala masiva · objetos económicos · datos estructurados y no estructurados · formatos abiertos · múltiples motores.
🏡
En el Lakehouse
Una base compartida para SQL, BI, streaming, ciencia de datos e IA, con menos duplicación entre plataformas.
🏢
Del Data Warehouse
Transacciones · esquemas controlados · gobierno · desempeño SQL · auditoría · datos preparados para negocio.
Convergencia. El objetivo no es borrar las diferencias entre cargas de trabajo, sino servirlas desde datos coherentes y gobernados.

Esta unión no significa que todos los datos deban tener el mismo grado de transformación. Un archivo recién recibido puede convivir con una tabla certificada para dirección, siempre que la arquitectura permita distinguir su nivel de calidad, controlar quién puede utilizarlo y rastrear cómo se produjo.

Para comprender cómo opera esta tecnología en la práctica, estudiaremos las cinco capas lógicas que integran una arquitectura de Data Lakehouse robusta.

6.4 Detalle Teórico de las Cinco Capas

A continuación, analizaremos en profundidad las responsabilidades técnicas de cada una de las cinco capas lógicas que estructuran esta arquitectura moderna:

6.4.1 1. Capa de Ingesta (Ingestion Layer)

Es el punto de entrada que conecta los múltiples orígenes de datos (estructurados, semi-estructurados o no estructurados) con la plataforma. Soporta dos modalidades operativas esenciales: * Procesamiento por Lotes (Batch): Cargas periódicas de datos acumulados a intervalos programados (por ejemplo, importaciones nocturnas de transacciones desde una base de datos PostgreSQL). * Procesamiento en Tiempo Real (Streaming): Captura y carga continua de datos a medida que se generan (por ejemplo, flujos de eventos de navegación web o lecturas de sensores industriales).

6.4.2 2. Capa de Almacenamiento (Storage Layer)

El Data Lakehouse implementa su almacenamiento físico directamente sobre un Data Lake conformado por sistemas de almacenamiento de objetos distribuidos y económicos (como Amazon S3, Google Cloud Storage o Azure ADLS). * Formatos Abiertos: A diferencia de los DWH clásicos (que encapsulan los datos en formatos binarios propietarios), el Lakehouse almacena los datos en archivos con especificaciones de código abierto y altamente eficientes para lectura columnar (como Apache Parquet u ORC). Esto evita la dependencia de un único proveedor (vendor lock-in).

6.4.3 3. Capa de Metadatos (Metadata Layer)

Es el núcleo innovador del Data Lakehouse. Consiste en una delgada capa lógica que gestiona metadatos estructurados sobre los archivos físicos del Data Lake, cerrando la brecha técnica respecto a un DWH relacional. Aporta: * Transacciones ACID: Garantiza que múltiples procesos puedan leer y escribir archivos Parquet de manera simultánea sin generar inconsistencias de datos o archivos corruptos. * Gobernanza y Cumplimiento: Valida de manera estricta que los datos que se escriben cumplan con el esquema esperado (Schema Enforcement), evitando el desorden o la degradación de datos. * Viaje en el Tiempo (Time Travel): Mantiene un historial de versiones de los metadatos, lo que permite ejecutar consultas sobre el estado exacto de los datos en un punto específico en el pasado.

6.4.4 4. Capa de APIs

Proporciona interfaces estándar de acceso para que diferentes herramientas consuman la información del almacenamiento de forma nativa sin necesidad de copiarla o moverla: * SQL APIs: Permite consultas directas con sintaxis SQL estándar utilizando motores optimizados de consulta (como Spark SQL o Photon). * Declarative Dataframe APIs: Provee interfaces de programación declarativas (como PySpark o Polars Dataframes) diseñadas para la transformación compleja de datos masivos. * Metadata APIs: Facilita la lectura directa del linaje de datos y los metadatos históricos para auditorías.

6.4.5 5. Capa de Consumo (Consumption Layer)

Es el nivel superior donde se genera el valor del negocio a partir de los datos consolidados. A diferencia de las arquitecturas tradicionales que requerían bases de datos distintas, el Lakehouse soporta directamente: * Business Intelligence (BI): Reportes interactivos y tableros en vivo (con herramientas como Metabase, Tableau o Power BI) consultando tablas con rendimiento de nivel de DWH. * Ciencia de Datos y Machine Learning: Acceso veloz en crudo para entrenamiento de modelos de Inteligencia Artificial (con Python, R o PyTorch) interactuando directamente con el almacenamiento columnar.

Las cinco capas deben leerse como responsabilidades y no necesariamente como cinco productos separados. Un servicio administrado puede cubrir varias de ellas, mientras que una arquitectura basada en componentes abiertos puede asignarlas a distintas herramientas. Lo importante es que el contrato entre capas sea explícito: dónde viven los datos, quién administra las tablas, qué motor procesa cada carga y dónde se aplican las políticas.

6.5 El componente decisivo: de archivos a tablas confiables

Un Data Lake tradicional puede contener miles de archivos Parquet correctamente organizados y, aun así, carecer de comportamiento transaccional. Si dos procesos escriben al mismo tiempo, un lector podría observar solo parte de una actualización. Tampoco existe, por el simple hecho de usar Parquet, un registro confiable de qué archivos forman una tabla en un instante determinado.

Los formatos de tabla modernos —como Apache Iceberg, Delta Lake y Apache Hudi— añaden metadatos y protocolos sobre los archivos. Estos protocolos describen versiones, esquemas, particiones y operaciones válidas. Gracias a ellos, el motor no necesita interpretar una carpeta como una colección accidental de archivos: puede tratarla como una tabla con identidad e historia.

📦 📦 📦
Archivos en objetos
Parquet, ORC y otros formatos almacenados en buckets.
→
📚
Formato de tabla + catálogo
Snapshots · esquema · transacciones · particiones · permisos · estadísticas.

✅
Tabla administrada

La innovación central del Lakehouse no es un nuevo tipo de disco, sino el protocolo que coordina cómo se interpretan y modifican los datos.

Esta distinción evita una confusión común: Parquet es un formato de archivo; Iceberg, Delta Lake o Hudi son formatos de tabla. El primero organiza columnas dentro de un archivo; los segundos coordinan conjuntos de archivos y sus cambios a lo largo del tiempo.

6.6 Arquitectura Medallion: Bronze, Silver y Gold

Una forma frecuente de organizar la calidad dentro del Lakehouse es la arquitectura de medallones. Los nombres Bronze, Silver y Gold no indican productos ni ubicaciones físicas obligatorias; representan estados progresivos de refinamiento. El patrón permite conservar evidencia original y, al mismo tiempo, publicar datos listos para decisiones.

🥉
Bronze · datos recibidos
Conserva la granularidad y el contenido de origen. Facilita auditoría, reprocesamiento y recuperación.
Ejemplo: eventos JSON tal como llegaron.
→
🥈
Silver · datos validados
Corrige tipos, deduplica, estandariza entidades y aplica reglas de calidad reutilizables.
Ejemplo: clientes unificados entre canales.
→
🥇
Gold · producto de datos
Publica métricas, agregaciones y modelos semánticos preparados para un caso de uso.
Ejemplo: venta neta diaria por región.
Refinamiento progresivo. La calidad aumenta sin perder la posibilidad de reconstruir el resultado desde su origen.

La capa Bronze no debe convertirse en un destino permanente para todo consumo; su función es preservar. Silver crea entidades reutilizables y coherentes. Gold materializa el lenguaje del negocio. Una misma organización puede tener varias tablas Gold, porque cada producto analítico responde a decisiones y niveles de agregación diferentes.

6.7 Separar almacenamiento y cómputo

La nube hizo viable otra propiedad fundamental: almacenar los datos una vez y asignar capacidad de cómputo según la carga. Un tablero ejecutivo, una transformación de Spark y el entrenamiento de un modelo requieren perfiles de procesamiento distintos. En un Lakehouse, esos motores pueden escalar de manera independiente y acceder a tablas gobernadas sobre la misma base de almacenamiento.

Esta separación aporta elasticidad, pero no significa que cualquier motor producirá el mismo desempeño. El formato de tabla, el catálogo, las estadísticas, el tamaño de los archivos, la partición y las cachés siguen siendo determinantes. La promesa correcta no es «un motor para todo», sino varios motores especializados sobre contratos de datos compartidos.

7 Lakehouse en plataformas modernas de nube

Las compañías rara vez implementan cada capa desde cero. Combinan servicios administrados de almacenamiento, catálogo, procesamiento, gobierno y consumo. Las tres nubes principales ofrecen rutas distintas hacia la misma idea arquitectónica: reducir la frontera entre lago y almacén sin renunciar a cargas SQL, ciencia de datos o IA.

7.1 Google Cloud: BigQuery, BigLake y almacenamiento abierto

En Google Cloud, BigQuery aporta el motor SQL administrado y sin servidores, mientras que BigLake extiende gobierno y acceso tabular hacia datos almacenados en Cloud Storage y, mediante capacidades multinube, hacia Amazon S3 o Azure Blob Storage. Las tablas administradas con Apache Iceberg permiten que los datos permanezcan en almacenamiento controlado por la organización y sean interoperables con otros motores. La documentación actual de Google presenta esta combinación como la base para Lakehouses abiertos sobre Iceberg. Véanse la introducción oficial a BigLake y las tablas administradas con Apache Iceberg.

BigQuery, por sí solo, también puede operar como un Data Warehouse moderno. La concepción Lakehouse aparece cuando el cómputo SQL, el almacenamiento de objetos, los formatos abiertos y el gobierno se conectan para consultar una misma base de datos sin exigir que toda la información se copie primero a tablas nativas.

7.2 Amazon Web Services: S3, catálogo, gobierno y varios motores

En AWS, Amazon S3 suele funcionar como almacenamiento base; AWS Glue Data Catalog registra las tablas y AWS Lake Formation centraliza permisos. Motores como Amazon Athena, Amazon Redshift Spectrum, Amazon EMR y AWS Glue pueden consultar o transformar datos gobernados. La arquitectura Lakehouse de Amazon también integra datos de S3 y del almacenamiento administrado de Redshift mediante catálogos, y expone tablas Apache Iceberg a motores compatibles. Véanse la arquitectura Lakehouse de Amazon y la documentación de AWS Lake Formation.

Este ecosistema ilustra una característica común del Lakehouse: la plataforma no es un solo servicio. S3 conserva los objetos, el catálogo describe los datos, Lake Formation aplica gobierno y los motores se eligen según la carga de trabajo.

7.3 Microsoft Azure: OneLake, Fabric y Azure Databricks

Microsoft ofrece más de una ruta. En Microsoft Fabric, OneLake proporciona un almacenamiento unificado construido sobre ADLS Gen2; los elementos Lakehouse organizan archivos y tablas, mientras que Spark, los puntos de conexión SQL y Power BI trabajan sobre esa base. Fabric utiliza Delta como formato abierto de tabla y busca reducir copias entre ingeniería, almacenes y BI. Véanse la descripción oficial de Microsoft Fabric y su arquitectura de Data Warehouse sobre OneLake.

Otra alternativa es Azure Databricks, donde Delta Lake aporta transacciones y control de esquema, Unity Catalog centraliza gobierno, Spark procesa ingeniería y ciencia de datos, y Databricks SQL atiende cargas analíticas. Microsoft define explícitamente este patrón como una combinación de las ventajas del lago y el almacén. Véase ¿Qué es un Data Lakehouse? en Azure Databricks.

7.4 Cómo leer estas equivalencias

No existe una traducción perfecta de un servicio a otro. BigQuery, Redshift, Athena, Fabric Warehouse y Databricks SQL no ocupan exactamente el mismo lugar ni tienen el mismo modelo operativo. Una comparación útil debe comenzar por las capacidades que necesita la organización:

  • ¿Dónde estarán físicamente los datos y quién controlará ese almacenamiento?
  • ¿Qué formato de tabla permitirá transacciones e interoperabilidad?
  • ¿Qué catálogo será la autoridad para esquemas, permisos y linaje?
  • ¿Qué motores atenderán SQL, streaming, ingeniería e IA?
  • ¿Cómo se controlarán costos, calidad, observabilidad y recuperación?

8 Ejemplo práctico: comercio digital

Supongamos que una empresa de comercio electrónico conserva transacciones en una base relacional, eventos de navegación en archivos JSON, imágenes de productos en almacenamiento de objetos y conversaciones de soporte en texto. El área financiera necesita ventas certificadas; marketing requiere sesiones casi en tiempo real; el equipo de ciencia de datos entrena modelos de recomendación.

En una arquitectura separada, cada equipo construiría copias y pipelines propios. En un Lakehouse, los eventos aterrizan en Bronze; las identidades de cliente, producto y sesión se validan en Silver; las métricas de venta, conversión y abandono se publican en Gold. BI consulta las tablas Gold, mientras que los modelos pueden combinar entidades Silver con datos no estructurados autorizados. Todos parten del mismo catálogo y de políticas comunes.

🛒 📱 💬
Eventos diversos
Compras, clics, catálogo, imágenes y conversaciones.
🏡
Lakehouse gobernado
Bronze conserva; Silver integra; Gold publica métricas y productos de datos.
📊 🧠 ⚡
Múltiples decisiones
Cierre financiero, tableros, recomendaciones y detección de anomalías.
Un mismo fundamento de datos puede servir productos diferentes sin imponer el mismo modelo de consumo a todos.

9 Beneficios, límites y decisiones de diseño

El Lakehouse puede disminuir duplicaciones y simplificar la arquitectura, pero no elimina el trabajo de ingeniería. Para obtener valor deben diseñarse contratos de datos, pruebas de calidad, políticas de acceso, mantenimiento de archivos, optimización de tablas, observabilidad y administración de costos.

Entre sus beneficios potenciales destacan:

  • Una fuente compartida para BI, ciencia de datos, streaming e IA.
  • Menor movimiento de datos entre repositorios analíticos.
  • Escalamiento independiente de almacenamiento y cómputo.
  • Uso de formatos abiertos y posibilidad de combinar motores.
  • Historia, auditoría y recuperación mediante versiones de tablas.

También presenta retos:

  • La interoperabilidad real depende de qué partes del formato soporta cada motor.
  • Muchos archivos pequeños, particiones deficientes o estadísticas incompletas degradan las consultas.
  • Un catálogo sin responsables ni políticas no resuelve por sí mismo el gobierno.
  • El consumo elástico puede elevar costos si no existen presupuestos, cuotas y observabilidad.
  • Una capa Gold mal diseñada puede reproducir los mismos silos que se buscaba eliminar.

10 Conclusión

El Data Lakehouse representa una concepción moderna de la plataforma analítica: toma al Data Lake como fundamento flexible y le añade las garantías que hicieron valioso al Data Warehouse. Su propósito no es declarar obsoletos los almacenes ni convertir todos los datos en una única tabla, sino reducir fronteras artificiales entre almacenamiento, análisis e inteligencia artificial.

Google Cloud, AWS y Microsoft materializan esta idea con combinaciones distintas de almacenamiento de objetos, formatos de tabla, catálogos, motores SQL, Spark y herramientas de gobierno. Las marcas y servicios evolucionan; los principios permanecen. Un Lakehouse bien diseñado debe conservar datos diversos, administrarlos como tablas confiables, permitir motores especializados y publicar productos de datos comprensibles para el negocio.

La pregunta arquitectónica final no es «¿qué herramienta compraremos?», sino «¿cómo lograremos que distintos equipos utilicen datos abiertos, gobernados y consistentes sin multiplicar copias ni definiciones?».
