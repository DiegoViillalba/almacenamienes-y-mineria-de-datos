18  Consumo Moderno de Data Marts: APIs y Capas Semánticas

De la consulta directa al contrato de servicio

Author

Diego Villalba

Published

August 5, 2026

El capítulo anterior terminó con el data mart de Ventas ya construido: cuatro tablas —dim_tiempo, dim_ubicacion, dim_departamento, fact_ventas— listas para responder preguntas de negocio mediante JOIN y GROUP BY, o mediante las operaciones de un cubo OLAP. Esa forma de consumo —un analista con acceso directo al motor de base de datos o a una herramienta de BI conectada por ODBC/JDBC— sigue siendo válida, pero no es la única, ni siempre la más adecuada. Una aplicación móvil de ventas, un panel embebido en el sitio de un cliente, otro microservicio de la organización o un agente automatizado no deberían necesitar credenciales de base de datos ni conocer el esquema interno del data mart para obtener una cifra de ventas. Este capítulo formaliza esa idea: exponer el data mart mediante un contrato de servicio —una API— en lugar de acceso directo a las tablas.

18.1 Del acceso directo al contrato de servicio

En el modelo de consumo tradicional, cada cliente (una hoja de cálculo, un dashboard, un script) se conecta directamente al data mart y ejecuta su propia consulta SQL. Este modelo es simple, pero acopla a cada cliente con los detalles internos del esquema: si dim_ubicacion cambia una columna de nombre, todos los clientes que la referencian se rompen. Además, es difícil aplicar de forma centralizada control de acceso, límites de uso o versionado.

Definición. Un contrato de servicio de datos desacopla la representación interna de almacenamiento \(DM_j\) de la interfaz que ven los clientes, mediante una función de acceso \(A\) que expone solo las operaciones y campos autorizados: \[ A: \text{Petición} \longrightarrow \text{Respuesta}, \qquad A \text{ no revela el esquema interno de } DM_j \]

Data Mart de Ventas

→
Capa semántica + API

Diagrama conceptual. Ningún cliente necesita conocer el esquema interno del data mart: todos consumen el mismo contrato.

Esta separación entre almacenamiento y consumo es la misma idea de independencia de datos que ya aparece en el diseño de un DW (Kimball and Ross 2013), llevada un nivel más arriba: así como el modelo dimensional independiza el análisis de los sistemas operacionales, la capa de API independiza a los clientes del modelo dimensional.

18.2 REST sobre un data mart

REST (Representational State Transfer) es el estilo arquitectónico definido por Roy Fielding para sistemas distribuidos basados en recursos, representaciones y operaciones sin estado sobre HTTP (Fielding 2000). En el contexto de un data mart, un recurso natural es una consulta agregada: por ejemplo, “ventas por región y trimestre”.

Definición. Un endpoint REST sobre un data mart mapea una combinación de filtros y agrupaciones a una representación (usualmente JSON): \[ \text{GET } /\text{ventas}?\text{region}=r\,\&\,\text{trimestre}=t \;\longmapsto\; \big\{\text{departamento}: v \;\big|\; v = C(r,t,\cdot)\big\} \]

Nótese el paralelismo con la función de cubo \(C\) del primer capítulo: el endpoint REST es, en esencia, una forma de invocar esa misma función agregada a través de HTTP, con los filtros codificados como parámetros de consulta.

Martin Fowler resume la madurez de una API REST en el Richardson Maturity Model: nivel 0 (un solo endpoint tipo RPC), nivel 1 (recursos individuales), nivel 2 (verbos HTTP y códigos de estado correctos) y nivel 3 (HATEOAS, enlaces de navegación embebidos en la respuesta) (Fowler 2010). La mayoría de las APIs analíticas en producción se detienen en el nivel 2, que ya resuelve el problema práctico de exponer datos de forma predecible.

18.2.1 Diseño del endpoint

Un endpoint de nivel 2 razonable para el data mart de Ventas podría verse así (código ilustrativo, no ejecutado en este documento, para evitar añadir dependencias nuevas al entorno del curso):

# app.py — ilustrativo, requiere fastapi (no incluido en requirements.txt del curso)
from fastapi import FastAPI, Query

app = FastAPI(title="API de Ventas")

@app.get("/v1/ventas")
def obtener_ventas(
    region: str | None = Query(None),
    trimestre: str | None = Query(None),
    departamento: str | None = Query(None),
):
    """Devuelve ventas agregadas filtradas por región, trimestre y/o departamento."""
    resultado = consultar_metrica(
        "total_ventas",
        group_by=["region", "trimestre", "departamento"],
        filtros={"region": region, "trimestre": trimestre, "departamento": departamento},
    )
    return {"data": resultado}

El detalle importante aquí no es la sintaxis de FastAPI (Ramírez, Sebastián 2024), sino la separación de responsabilidades: el endpoint solo traduce parámetros HTTP en una llamada a consultar_metrica, una función de capa semántica que se define y prueba una sola vez (se implementa más adelante en este capítulo) y que oculta por completo los JOIN y GROUP BY del data mart.

Ahora se define, en Python puro, la función que un endpoint REST invocaría internamente, y se simula una petición GET /v1/ventas?region=Centro&trimestre=T2:

def obtener_ventas(region=None, trimestre=None, departamento=None):
    df = data_mart
    if region:
        df = df[df["region"] == region]
    if trimestre:
        df = df[df["trimestre"] == trimestre]

18.3 GraphQL sobre un data mart

GraphQL es un lenguaje de consulta en el que el cliente, no el servidor, decide la forma exacta de la respuesta: qué campos quiere y con qué nivel de anidamiento, en una sola petición a un único endpoint (GraphQL Foundation 2021). Esto evita dos problemas comunes en REST: el over-fetching (recibir campos que no se necesitan) y el under-fetching (necesitar varias peticiones encadenadas para reunir toda la información).

Definición. Una consulta GraphQL especifica un subconjunto de campos \(F \subseteq \text{campos}(R)\) de un recurso \(R\); el resolutor devuelve únicamente \(F\), sin importar cuántos campos adicionales exponga el esquema.

Un esquema típico sobre el data mart de Ventas (código ilustrativo; requeriría una librería como strawberry-graphql o graphene, no incluida en el entorno del curso):

# schema.py — ilustrativo, requiere strawberry-graphql
import strawberry

@strawberry.type
class VentaAgregada:
    region: str
    trimestre: str
    departamento: str
    total_ventas: float

@strawberry.type
class Query:
    @strawberry.field
    def ventas(self, region: str | None = None, trimestre: str | None = None) -> list[VentaAgregada]:
        resultado = consultar_metrica(
            "total_ventas",
            group_by=["region", "trimestre", "departamento"],
            filtros={"region": region, "trimestre": trimestre},
        )
        return [VentaAgregada(**fila) for fila in resultado]

schema = strawberry.Schema(query=Query)

Un cliente que solo necesita el total por departamento, sin región ni trimestre, escribiría:

query {
  ventas(region: "Centro", trimestre: "T2") {
    departamento
    totalVentas
  }
}

18.3.1 Simulación reproducible: el cliente decide la forma de la respuesta

El siguiente código, ejecutado con pandas puro, reproduce el comportamiento esencial de un resolutor GraphQL: recibe la misma consulta y los mismos filtros que en el ejemplo REST, pero un parámetro adicional —los campos solicitados por el cliente— determina qué columnas trae la respuesta.

def resolver_ventas(campos_solicitados, region=None, trimestre=None, departamento=None):
    df = data_mart
    if region:
        df = df[df["region"] == region]
    if trimestre:
        df = df[df["trimestre"] == trimestre]
    if departamento:
        df = df[df["departamento"] == departamento]

    agregado = (
        df.groupby(["region", "trimestre", "departamento"], as_index=False)["monto_venta"]
        .sum()
        .rename(columns={"monto_venta": "total_ventas"})
    )
    return agregado[campos_solicitados].to_dict(orient="records")

# El cliente REST recibía region, trimestre, departamento y total_ventas.
# El cliente GraphQL pide solo lo que necesita:
resolver_ventas(["departamento", "total_ventas"], region="Centro", trimestre="T2")
[{'departamento': 'Decoración', 'total_ventas': 22},
 {'departamento': 'Eléctrico', 'total_ventas': 28},
 {'departamento': 'Madera', 'total_ventas': 50},
 {'departamento': 'Plomería', 'total_ventas': 60}]

La misma pregunta de negocio —ventas del Centro en T2— produce una respuesta más pequeña porque el cliente, no el servidor, definió la forma de la salida. Esta flexibilidad es la principal ventaja de GraphQL; su costo es una capa de resolución más compleja y, en resolutores mal diseñados, el riesgo del problema N+1 (una consulta adicional por cada elemento anidado) (Kleppmann 2017).

18.4 Capa semántica: métricas como código

Tanto el ejemplo REST como el de GraphQL delegaron el cálculo real a una función llamada consultar_metrica. Esa función es la pieza más importante de una arquitectura de consumo moderna: la capa semántica. Su función es definir cada métrica de negocio (qué se suma, con qué filtros válidos, con qué nombre) una sola vez, para que REST, GraphQL, un notebook y una herramienta de BI calculen exactamente el mismo número (dbt Labs 2024; Cube Dev, Inc. 2024).

Definición. Una métrica semántica es una función registrada \(M: (\text{agrupación}, \text{filtros}) \to \mathbb{R}\) sobre el data mart, independiente de cualquier consumidor específico. \[ M_{\text{total\_ventas}}(G, F) = \sum_{i \,:\, i \models F} \text{monto\_venta}_i \quad \text{agrupado por } G \]

Esta idea es el equivalente, a nivel de métricas, de lo que las dimensiones conformadas son a nivel de atributos (capítulo anterior): en lugar de que cada equipo reimplemente su propio cálculo de “ventas totales” dentro de cada API o cada dashboard, existe una sola definición autorizada. A esta arquitectura —métricas versionadas como código, consumidas por múltiples herramientas de presentación— se le conoce como headless BI.

18.4.1 Implementación reproducible de un registro de métricas

METRICAS = {
    "total_ventas": {
        "columna": "monto_venta",
        "agregacion": "sum",
    },
    "ticket_promedio": {
        "columna": "monto_venta",
        "agregacion": "mean",
    },
}

def consultar_metrica(nombre_metrica, group_by, filtros=None):
    if nombre_metrica not in METRICAS:
        raise ValueError(f"Métrica no registrada: {nombre_metrica}")

    definicion = METRICAS[nombre_metrica]
    df = data_mart

    for campo, valor in (filtros or {}).items():
        if valor is not None:
            df = df[df[campo] == valor]

    agregado = (
        df.groupby(group_by, as_index=False)[definicion["columna"]]
        .agg(definicion["agregacion"])
        .rename(columns={definicion["columna"]: nombre_metrica})
    )
    return agregado.to_dict(orient="records")

consultar_metrica(
    "total_ventas",
    group_by=["region", "trimestre"],
    filtros={"trimestre": "T2"},
)
[{'region': 'Centro', 'trimestre': 'T2', 'total_ventas': 160},
 {'region': 'Norte', 'trimestre': 'T2', 'total_ventas': 146},
 {'region': 'Occidente', 'trimestre': 'T2', 'total_ventas': 160},
 {'region': 'Sureste', 'trimestre': 'T2', 'total_ventas': 125}]
consultar_metrica(
    "ticket_promedio",
    group_by=["departamento"],
    filtros={"region": "Centro"},
)
[{'departamento': 'Decoración', 'ticket_promedio': 21.0},
 {'departamento': 'Eléctrico', 'ticket_promedio': 29.0},

 {'departamento': 'Plomería', 'ticket_promedio': 50.0}]

Con este registro, tanto obtener_ventas (REST) como resolver_ventas (GraphQL) podrían reescribirse para llamar únicamente a consultar_metrica, garantizando que ambos protocolos devuelvan cifras consistentes entre sí y con cualquier otra herramienta —incluido el cubo OLAP del primer capítulo— que también consulte el mismo registro.

18.6 Seguridad y gobierno en la capa de API

Exponer un data mart mediante una API centraliza también el lugar natural para aplicar controles que serían difíciles de garantizar si cada cliente consultara la base de datos directamente:

  • Autenticación y autorización. Cada petición debe identificar quién la hace (token, llave de API) y qué puede ver.
  • Seguridad a nivel de fila (row-level security). Por ejemplo, un gerente regional solo debería poder consultar region = "su región", sin importar qué parámetros envíe.
  • Límites de uso (rate limiting). Evita que una consulta costosa mal escrita degrade el servicio para el resto de los clientes.
  • Versionado explícito del contrato. El prefijo /v1/ en los ejemplos anteriores permite evolucionar el esquema sin romper clientes existentes.
  • Documentación ejecutable. Un esquema OpenAPI (para REST) o el esquema introspectable de GraphQL permiten generar documentación siempre sincronizada con el código.

18.7 Ventajas, limitaciones y buenas prácticas

Exponer un data mart mediante APIs y una capa semántica tiene ventajas claras frente al acceso directo:

  • Desacoplamiento: cambios en el esquema físico del data mart no rompen a los clientes si el contrato se mantiene.
  • Reutilización: un mismo conjunto de métricas alimenta apps, dashboards y otros servicios sin duplicar lógica de agregación.
  • Consistencia: una sola definición de cada métrica evita que dos equipos reporten cifras distintas para la misma pregunta.
  • Gobierno centralizado: autenticación, autorización y límites de uso se aplican en un solo lugar.

También introduce costos que conviene anticipar:

  • Una capa adicional de infraestructura que hay que operar y monitorear.
  • Riesgo de latencia si cada petición recalcula agregaciones costosas en lugar de usar resultados pre-agregados o cacheados.
  • En GraphQL, riesgo de consultas anidadas ineficientes si los resolutores no se diseñan con cuidado.

Buenas prácticas recomendadas:

  1. Definir las métricas en la capa semántica antes de escribir cualquier endpoint, nunca al revés.
  2. Versionar el contrato de la API igual que se versiona el esquema del data mart.
  3. Pre-agregar o cachear las consultas más frecuentes en lugar de recalcularlas en cada petición.
  4. Aplicar seguridad a nivel de fila en la capa semántica, no confiar en que cada cliente filtre correctamente.
  5. Tratar cada data mart expuesto como un producto de datos, con dueño, documentación y garantías de calidad (Dehghani 2022).

18.8 Conclusiones

Este capítulo cerró el recorrido de la sección de modelado para consumo: partiendo de un data mart bien diseñado, existen (al menos) dos formas complementarias de consumirlo. La primera, cubierta en el primer capítulo, es la navegación interactiva mediante un cubo OLAP: slice, dice, roll-up, drill-down y pivot sobre una vista multidimensional, pensada para un analista humano explorando datos. La segunda, cubierta aquí, es la integración programática mediante un contrato de servicio —REST o GraphQL— respaldado por una capa semántica que garantiza que la definición de cada métrica sea única, sin importar cuántas aplicaciones distintas la consulten.

Ambas formas de consumo parten exactamente del mismo data mart. La elección entre exponer un cubo, una API o ambos no es una decisión tecnológica aislada: depende de quién necesita los datos y cómo los va a usar. Un director que explora tendencias trimestre a trimestre se beneficia de un cubo interactivo; una aplicación móvil que muestra el total de ventas del día se beneficia de un endpoint REST ligero; un ecosistema de aplicaciones internas con necesidades de datos heterogéneas se beneficia de una capa semántica expuesta vía GraphQL. Diseñar bien el data mart y sus dimensiones conformadas es lo que hace posible que las tres alternativas coexistan sin contradecirse entre sí.
