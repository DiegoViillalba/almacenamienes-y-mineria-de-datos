18  Modern Data Mart Consumption: APIs and Semantic Layers

From Direct Queries to Service Contracts

Author

Diego Villalba

Published

September 1, 2026

The previous chapter concluded with the construction of a physical Sales data mart comprising four core tables: dim_tiempo, dim_ubicacion, dim_departamento, and fact_ventas. While querying this dimensional schema directly via SQL or BI tools connected through ODBC/JDBC remains common, it is not the only—nor always the most effective—consumption pattern. Mobile applications, embedded customer dashboards, microservices, and autonomous software agents should not require direct database credentials or internal schema knowledge to retrieve sales metrics. This chapter formalizes exposing data marts through a service contract—an API layer—rather than direct database access.

18.1 From Direct Access to Service Contracts

In traditional consumption models, every client application connects directly to the data warehouse and executes custom SQL queries. While simple initially, this tightly couples client applications to internal physical schemas: renaming a column in dim_ubicacion breaks every downstream client. Furthermore, enforcing centralized access control, rate limiting, and schema versioning becomes difficult.

Definition. A data service contract decouples the physical storage representation \(DM_j\) from client-facing interfaces via an access function \(A\) that exposes only authorized operations and attributes: \[ A: \text{Request} \longrightarrow \text{Response}, \qquad A \text{ encapsulates the internal schema of } DM_j \]

Sales Data Mart

Architectural flow. Clients consume a unified service contract without needing direct database access or internal schema awareness.

This separation between storage and consumption extends classic data independence principles to the API layer (Kimball and Ross 2013).

18.2 REST APIs over Data Marts

REST (Representational State Transfer) maps operational resources and analytical queries to stateless HTTP endpoints (Fielding 2000). For a data mart, a natural REST resource is an aggregated metric query (e.g., “sales by region and quarter”).

Definition. A REST endpoint over a data mart maps filter parameters and dimension groupings to a structured payload (typically JSON): \[ \text{GET } /\text{sales}?\text{region}=r\,\&\,\text{quarter}=t \;\longmapsto\; \big\{\text{department}: v \;\big|\; v = C(r,t,\cdot)\big\} \]

The Richardson Maturity Model categorizes REST API maturity from Level 0 (single RPC endpoint) to Level 3 (HATEOAS hypermedia controls) (Fowler 2010). Most enterprise analytical APIs operate at Level 2, leveraging HTTP verbs and status codes alongside query parameter filtering.

18.2.1 Endpoint Interface Design

A Level 2 REST endpoint interface for the Sales data mart:

# app.py — illustrative interface using FastAPI
from fastapi import FastAPI, Query

app = FastAPI(title="Sales Analytics API")

@app.get("/v1/sales")
def get_sales(
    region: str | None = Query(None),
    quarter: str | None = Query(None),
    department: str | None = Query(None),
):
    """Returns aggregated sales filtered by region, quarter, and/or department."""
    result = query_metric(
        "total_sales",
        group_by=["region", "quarter", "department"],
        filters={"region": region, "quarter": quarter, "department": department},
    )
    return {"data": result}

The key architectural pattern here is separation of concerns: the HTTP endpoint delegates metric calculation to query_metric, an underlying semantic layer function that abstracts SQL join execution (Ramírez, Sebastián 2024).

Implementing the endpoint request handler:

def get_sales_endpoint(region=None, quarter=None, department=None):
    df = data_mart
    if region:
        df = df[df["region"] == region]
    if quarter:
        df = df[df["quarter"] == quarter]
    if department:

18.3 GraphQL APIs over Data Marts

GraphQL empowers client applications to request specific fields and structure responses dynamically in a single request, resolving REST over-fetching (retrieving unneeded attributes) and under-fetching (requiring multiple round-trips) (GraphQL Foundation 2021).

Definition. A GraphQL query specifies a subset of fields \(F \subseteq \text{fields}(R)\) on resource \(R\); the server resolver returns strictly \(F\).

Illustrative GraphQL schema definition:

# schema.py — illustrative Strawberry GraphQL definition
import strawberry

@strawberry.type
class AggregatedSale:
    region: str
    quarter: str
    department: str
    total_sales: float

@strawberry.type
class Query:
    @strawberry.field
    def sales(self, region: str | None = None, quarter: str | None = None) -> list[AggregatedSale]:
        result = query_metric(
            "total_sales",
            group_by=["region", "quarter", "department"],
            filters={"region": region, "quarter": quarter},
        )
        return [AggregatedSale(**row) for row in result]

schema = strawberry.Schema(query=Query)

Client GraphQL query requesting only department and total_sales:

query {
  sales(region: "Central", quarter: "Q2") {
    department
    totalSales
  }
}

18.4 Semantic Layers: Metrics as Code

Both REST and GraphQL patterns rely on an underlying semantic layer. A semantic layer defines business metrics (calculation rules, aggregations, filters) once as code, serving as a single source of truth across dashboards, REST endpoints, GraphQL queries, and notebooks (dbt Labs 2024; Cube Dev, Inc. 2024).

Definition. A semantic metric is a registered function \(M: (\text{groupings}, \text{filters}) \to \mathbb{R}\) executed over the underlying data mart: \[ M_{\text{total\_sales}}(G, F) = \sum_{i \,:\, i \models F} \text{sales\_amount}_i \quad \text{grouped by } G \]

Decoupling metric definitions from visualization tools is commonly referred to as headless BI.

18.4.1 Reproducible Semantic Metric Registry

METRICS_REGISTRY = {
    "total_sales": {
        "column": "sales_amount",
        "aggregation": "sum",
    },
    "average_ticket": {
        "column": "sales_amount",
        "aggregation": "mean",
    },
}

def query_metric(metric_name, group_by, filters=None):
    if metric_name not in METRICS_REGISTRY:
        raise ValueError(f"Unregistered metric: {metric_name}")

    definition = METRICS_REGISTRY[metric_name]
    df = data_mart

    for field, value in (filters or {}).items():
        if value is not None:
            df = df[df[field] == value]

    aggregated = (
        df.groupby(group_by, as_index=False)[definition["column"]]
        .agg(definition["aggregation"])
        .rename(columns={definition["column"]: metric_name})
    )
    return aggregated.to_dict(orient="records")

query_metric(
    "total_sales",
    group_by=["region", "quarter"],
    filters={"quarter": "Q2"},
)

18.6 Security and Governance at the API Layer

Centralizing data mart access through an API layer enables security controls that are difficult to enforce with direct database queries:

  • Authentication & Authorization: Verifies caller identities and scope permissions (JWT, API keys).
  • Row-Level Security (RLS): Automatically restricts data visibility based on user roles (e.g., regional managers see only their assigned regions).
  • Rate Limiting & Throttling: Protects analytical databases from unoptimized, expensive queries.
  • Contract Versioning: Explicit URL paths (e.g., /v1/) support schema evolution without breaking legacy client integrations.

18.7 Conclusions

Exposing data marts via APIs and semantic layers transforms database tables into governed data products (Dehghani 2022). Whether providing interactive OLAP cube exploration or programmatic REST/GraphQL service endpoints, defining conformed dimensions and metrics once guarantees enterprise-wide consistency across all analytics consumers.
