8  Dimensional Schemas and Redundancy

The previous chapter covered facts, dimensions, granularity, and additivity. Now, we examine how dimensions are physically structured around fact tables: their degree of normalization, accepted level of redundancy, and the concrete impact of these decisions on storage costs and query performance.

8.1 Star Schema

A star schema consists of a central fact table directly connected to multiple dimension tables. Dimension tables are typically denormalized (controlled redundancy) to minimize joins and optimize analytical query speed.

In our academic example, the student dimension includes attributes like major and department within the same table, simplifying queries such as “average grade by major and semester”. The trade-off is accepting string repetition (e.g., repeating “Science” across thousands of student rows).

Structurally, the model is represented as follows:

In this schema:

  • The fact table resides at the center.
  • All dimensions connect directly to the fact table.
  • No relationships exist between dimension tables.
  • Hierarchical information (e.g., major → department) is denormalized directly inside the dimension table.

8.2 Snowflake Schema

A snowflake schema normalizes dimension tables into sub-dimensions. For example, separating “major” and “department” into distinct hierarchical tables removes data repetition, but increases query complexity and join overhead.

In this schema:

  • The student dimension no longer holds the department string directly.
  • Major and department are modeled as independent entities.
  • Data redundancy is minimized.
  • The number of joins required for queries involving department attributes increases.

8.2.1 Conceptual Comparison

Aspect Star Schema Snowflake Schema
Normalization Low (Denormalized) High
Redundancy Controlled Minimized
Join Count Lower Higher
Conceptual Complexity Simpler More Structured
OLAP Performance Generally Higher May Decrease
Data Governance More Flexible More Rigidly Controlled

8.2.2 Code Comparison in SQL

Using a sales domain, the operational difference between schemas appears directly in SQL queries:

-- Star Schema: One join per dimension
select
  d.year,
  p.category,
  sum(f.amount) as sales
from fact_sales as f
join dim_date as d using (date_key)
join dim_product as p using (product_key)
group by d.year, p.category;
-- Snowflake Schema: dim_product lacks "category", requiring an extra join step
select
  d.year,
  c.category,
  sum(f.amount) as sales
from fact_sales as f
join dim_date as d using (date_key)
join dim_product as p using (product_key)
join dim_category as c using (category_key)
group by d.year, c.category;
Criterion Star Schema Snowflake Schema
Querying Simple, fewer joins More joins required
Redundancy Higher Lower
Maintenance Direct More entities and keys
Recommended Use BI and self-service analytics Very large or shared hierarchies

8.3 Controlled Redundancy: The Real Cost of Denormalization

Traditional database literature presents normalization as an absolute good because data repetition consumes disk space. In modern columnar storage engines (Parquet, Delta, BigQuery, Snowflake), that repetition carries negligible storage cost.

Columnar engines do not store raw text strings repeatedly; they apply dictionary encoding (storing unique strings once in a dictionary and writing short integer codes per row) alongside run-length encoding (RLE) over sorted or low-cardinality columns. If dim_product contains 500,000 rows and category contains 20 unique values, the engine does not write “Electronics” 25,000 times: it stores the 20-category dictionary once, and writes tiny integer indexes per row.

In practice:

  • Storing category directly in dim_product (Star Schema) costs nearly the same storage space as storing category_key (Snowflake Schema)—both end up as small integers on disk.
  • Storage savings promised by normalization are marginal in modern columnar storage compared to 1990s row-oriented relational engines.
  • The meaningful trade-off between Star and Snowflake schemas is not storage volume, but query execution cost.

8.4 Query Execution Cost: Joins and Cloud Engines

The technical argument for Star Schema is not “it uses less disk space”, but “each query executes fewer join operations”. This becomes critical when dimension tables grow large.

Consider a customer dimension with 5 million rows, normalized as dim_customer → dim_city → dim_state (a snowflake geographic hierarchy) versus a denormalized star dimension where state sits directly on dim_customer.

To answer “total sales by state”:

  • Star Schema: fact_sales (100M rows) joins once with dim_customer (5M rows), which already contains state.
  • Snowflake Schema: fact_sales joins with dim_customer (5M rows), and that large intermediate result joins with dim_city (5K rows), and then with dim_state (32 rows).

The second query is not expensive because of the small sub-dimension tables (dim_city, dim_state)—it is expensive because it introduces network shuffle stages across intermediate join results of size matching fact_sales. Every extra hop in a join chain moves massive intermediate datasets across cluster networks.

This impacts cloud billing directly:

  • BigQuery charges per byte processed/scanned; complex join chains across large intermediate results increase bytes scanned and slot usage.
  • Snowflake charges per active warehouse compute time (credits); longer join chains increase warehouse execution duration.

Rule of Thumb: Denormalization redundancy in a star schema is inexpensive because it is stored once during ETL loading. The cost of an additional join step is paid on every single query execution, multiplied by query frequency. Therefore, BI data marts strongly favor star schemas, while snowflake schemas are reserved for massive hierarchies shared across multiple data marts where maintaining a single source of truth outweighs per-query execution costs.

8.5 Fact Constellation (Galaxy Schema)

When multiple business processes share common dimensions, they should share physical dimension tables—a structure known as a fact constellation or galaxy schema. Instead of an isolated star schema per process, multiple fact tables link to a set of conformed dimensions (identical surrogate keys, grain, and definitions across all referencing facts).

In a healthcare domain: beyond FACT_APPOINTMENT_CANCELLATION (one row per scheduled appointment), a hospital also logs FACT_HOSPITAL_BILLING (one row per billed line item). Rather than creating redundant dimensions for the second process, both fact tables share DIM_DATE, DIM_HOSPITAL, DIM_SERVICE, DIM_PATIENT, and DIM_INSURER:

Conformed dimensions eliminate redundant modeling effort: without them, separate teams build conflicting “patient” or “service” tables with different surrogate keys, preventing cross-process queries (e.g., “how many cancelled appointments still generated partial billing?”). Conformed dimensions make facts directly comparable.

The diagram presents six design patterns balancing query complexity and data redundancy.

Conformed Dimensions. A single physical dimension (same grain, keys, and definitions) shared across multiple fact tables, such as DIM_DATE above. It forms the backbone of galaxy schemas, preventing separate data marts from redefining “customer” or “product” independently.

Degenerate Dimensions. Transactional keys (e.g., invoice number, order ticket ID) stored directly in the fact table without separate dimension tables when no additional descriptive attributes exist.

Junk Dimensions. Combining multiple low-cardinality flags or status indicators (is_promo, payment_method, channel) into a single composite dimension table, preventing fact table column bloat.

Role-Playing Dimensions. A single physical dimension table referenced multiple times under different context roles in a fact table—for example, DIM_DATE referenced via order_date_key, ship_date_key, and payment_date_key.

Mini-Dimensions. Separating rapidly changing or volatile attributes (e.g., customer risk score or credit limit) into a standalone mini-dimension to prevent high-frequency Type 2 SCD updates across a large customer dimension table.

Bridge Tables. Resolving many-to-many relationships (e.g., a student with multiple active scholarships or a patient episode with multiple attending physicians) without duplicating fact rows or introducing artificial cardinality.

8.7 Conclusion

Star, Snowflake, and Constellation schemas represent distinct architectural choices shifting costs across storage, join execution, and maintenance complexity. In modern columnar storage engines, dimension denormalization is typically the most cost-effective approach. The remaining design challenge is handling attribute updates when dimensions change over time—the focus of the next chapter on Slowly Changing Dimensions (SCD).
